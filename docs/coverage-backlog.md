## 3. Deliberately not automated

| What | Reason |
|---|---|
| TC6 Contact Us, TC10/TC11 Subscription, TC21 Add review | Each submits data to the shared public site (a contact message plus file upload, a newsletter subscription, a product review) and there is **no API or UI path to delete it**. Running these on every push and PR would build up junk on someone else's site, against the repo's "leaves no data behind" principle. They are fine as a one-off manual/exploratory check, not as CI tests |
| TC14, TC15 (register while/before checkout) as separate specs | Covered by composition. `register.spec.ts` proves the UI registration form, `place-order-login.spec.ts` proves cart → checkout modal → auth → checkout → payment, and the API lifecycle proves account creation. A separate spec would spend 1–2 of the 10-spec budget repeating the same journey |
| TC7 Verify Test Cases page | Static link to a static page. No state and no user journey, so low regression value for a slot in the budget |
| TC25/TC26 scroll up with/without arrow | Tests browser scrolling more than application logic. Smooth-scroll animation pushes toward timing waits (banned by rule 7), and the regression value is too low to earn a budget slot |
| `getUserDetailByEmail` with any made-up email, or a DDT matrix on it | Rule 2: "garbage" emails (`""`, `notanemail`, `<script>...`) were confirmed to be **real accounts with other people's PII**. Only our own unique timestamped emails (`14c`, proposed `14e`) |
| `createAccount` with present-but-weird values (bad email format, XSS in names, over-long fields, non-numeric dates) | Rule 3: each one **creates a real account** (confirmed live). Only the missing-required-field matrix is safe and deterministic |
| Null-byte search (`"top\0dress"` → 4 results) | Rule 5: undocumented mechanism. Already recorded in README as an exploratory finding |
| verifyLogin/deleteAccount case-sensitivity or whitespace variants of our *own* email (e.g. `AE_...@EXAMPLE.COM`) | Undocumented behaviour (rule 5). Fine for exploration, but whichever answer comes back would be pinning an implementation detail |
| Cart quantity boundaries (0, negative, 1000+) and payment-form validation (invalid card numbers, past expiry) | No documented expected behaviour. The site accepts any card, so asserting either way pins undocumented behaviour. Exploratory only |
| A6 "update succeeds with wrong password", if live verification shows that | It would be a security finding to document in README, not an expected result to encode |
| Exact catalog counts (34 products, 8 brands, 14 "top" results in UI) and the `"Rs. "` price format | Data and formatting owned by the site, not a documented contract. Assert structure, sets and invariants instead |
